# W1 Failure Correlation and Admission Diagnostics

**Date:** 2026-09-19. Advances [AAPI-91–95](Async%20Public%20API%20Decisions.md#aapi-91-failure-context-is-an-immutable-diagnostic-snapshot) without freezing or exposing the W3 public declarations. The [completion audit](W1%20Completion%20Audit.md) retains the remaining operation-family, classification, telemetry and performance obligations.

## Immutable identity through reporting and recovery

[ExecutionFailure](../../../../src/DataLinq/Execution/ExecutionFailure.cs) now carries an internal operation kind, provider telemetry-instance identifier and optional conflicting active operation. Secondary entries carry their own operation kind. The vocabulary is separate from mutation implementation state; public namespaces/types, exact enum values and package consumers remain W3 work.

The collector captures primary correlation when it observes the exception. A later outer callback or cleanup report can supply missing information without relabeling compatible inner operation/provider evidence. The current execution boundary remains authoritative for transaction identity: an exception reused from a different transaction or known different provider cannot import that old identity, operation or conflicting active operation. In that case the actual reporting boundary supplies the operation/provider instead. A secondary exception cannot become the primary correlation source. Importing an earlier secondary snapshot preserves its recorded operation even if the exception itself has since acquired another context. Existing snapshots remain unchanged when the collector grows, an exception receives a newer context, or transaction recovery publishes an updated snapshot.

Direct-only exception lookup, original exception identity/stack, encounter order, reference-based deduplication and cleanup safety facts are preserved. Recovery copies correlation while updating completion/recovery policy; it does not relabel an inner query as a callback. No string/message/SQL parsing infers an operation. Unknown or unbound operations remain `Unknown` until their actual entry boundary supplies a kind.

Contexts copy identifiers and enums rather than retaining a provider, transaction, gate, connection or command. No SQL, connection string, parameters or raw keys are added. Original provider/application exceptions can still contain sensitive data and are not automatically sanitized or serialized.

## Admission conflicts do not modify active work

[TransactionOperationGate](../../../../src/DataLinq/Execution/TransactionOperationGate.cs) captures the existing provider telemetry ID when the managed transaction constructs it. Admission accepts an explicit operation kind separately from its human-readable message. Private steps and ownership transfers preserve that kind and provider identity; no ambient context or command-tagged bypass is introduced.

Overlap errors receive their own `InvalidOperation`/`Validation` snapshot. It identifies the rejected kind and the active kind, and advertises only `FinishActiveOperation` while an owner remains active. A helper-owned or closed-admission rejection without active work advertises `None`. The gate does not know database completion certainty and reports `Unknown` rather than guessing from admission state. Earlier snapshots remain historical facts after the active owner finishes; they are not continuing permissions to bypass validation.

Reporting occurs under the gate lock using copied identifiers, without calling provider code or publishing into the active transaction's failure state. The rejected call cannot poison, dispose, release or replace the admitted operation. The normal fail-fast admission/lifetime behavior is unchanged.
