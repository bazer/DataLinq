# W0 I/O Execution Map

This is a source audit of **7e36614b5f26f1dd199ff93bc60620f4b0714d5f**, the synchronous development baseline. It does not describe shipped async APIs. The accepted additions and exclusions remain in the [signature inventory](Async%20Signature%20Inventory%20and%20Compatibility%20Matrix.md); [W0 evidence](W0%20Baseline%20Evidence.md) records execution results and limitations.

Source links below are pinned to that commit. Existing tests describe regression coverage, not proof that the future async orchestration works.

## Shared Provider Boundaries

| Boundary | Current execution and ownership | W1/W2 obligation |
| --- | --- | --- |
| Nontransactional open | [SQLiteDbAccess](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.SQLite/SQLiteDbAccess.cs) creates/opens a connection and executes the committed-visibility PRAGMA. [SqlDbAccess](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.MySql/Shared/SqlDbAccess.cs) opens a pooled MySqlDataSource connection. Failure before reader handoff disposes the connection. | Native MySqlDataSource.OpenConnectionAsync; SQLite has synchronous underlying I/O. Cancellation during open, setup and cleanup must be separately tested. |
| Scalar/non-query | Access object assigns the connection to the supplied command, executes synchronously, then closes/disposes its connection. The IDbCommand overload borrows the command; string overloads own/dispose the command they create. | MySqlCommand.ExecuteScalarAsync/ExecuteNonQueryAsync; SQLite async-shaped methods do not supply nonblocking I/O. Preserve caller command ownership and exception identity. |
| Reader acquisition | Nontransactional ExecuteReader uses CloseConnection. Successful reader creation transfers connection closing to the reader. Transaction readers use the existing transaction connection; reader disposal must not complete it. | ExecuteReaderAsync and ReadAsync with the effective token; test acquisition failure, early termination, row failure and cleanup failure separately. |
| String/raw reader command ownership | [DatabaseAccess](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Database/DatabaseAccess.cs) transfers internally created commands to [OwnedCommandDataReader](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Database/OwnedCommandDataReader.cs). It disposes a command if acquisition fails. The wrapper disposes reader before command, exactly once, preserving both failures if necessary. Caller-supplied commands remain borrowed. | Add explicit async reader/command ownership without changing old synchronous interfaces or turning unsupported extensions into implicit sync fallbacks. |
| Row read/decoding | [SQLiteDataLinqDataReader](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.SQLite/SQLiteDataLinqDataReader.cs) and [SqlDataLinqDataReader](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.MySql/Shared/SqlDataLinqDataReader.cs) call provider Read and Dispose synchronously. Typed conversion/materialization runs after each read. SQLite GetBytes clones the driver's cached array; MySQL also exposes the optional owned-buffer capability. | Await row advancement, preserve conversion order and buffer ownership; do not assume an arbitrary legacy reader supports async or owned buffers. |
| Telemetry | DatabaseAccess wraps command execution with activity, exception and duration recording. Reader acquisition timing does not encompass all subsequent reads or connection opening. SQLite setup PRAGMAs are separate commands. Mutation/transaction metrics have their own boundaries. | Preserve workload meaning and add the accepted async stages without counting fewer commands as a speed improvement. Test telemetry under cancellation and partial completion. |

The pinned package graph uses **MySqlConnector 2.6.2** and **Microsoft.Data.Sqlite 10.0.11**. Local package XML/API inspection confirms the provider calls listed above, MySqlConnection.BeginTransactionAsync, MySqlTransaction.CommitAsync/RollbackAsync/DisposeAsync, and SQLite's synchronous BeginTransaction isolation/deferred overload. Inherited ADO.NET async members alone do not establish native capability.

Microsoft explicitly documents that [SQLite async ADO.NET methods execute synchronously](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async). Preserve the current `BeginTransaction(Serializable, deferred: true)` behavior: replacing it mechanically with an inherited async overload is not proof of equivalent transaction semantics. MySqlConnector documents [native opening](https://mysqlconnector.net/api/mysqlconnector/mysqlconnection/openasync/) and [command cancellation](https://mysqlconnector.net/overview/command-cancellation/); its soft/hard cancellation behavior does not prove DataLinq recovery or completion certainty. W2 must test those against the pinned driver and supported servers. No Task.Run facade is proposed.

## Query, Prepared And Raw Execution

**Owner: W1 execution contracts → W2 provider implementation → W3 public/generated APIs.**

- **Expression queries and terminals (S1).** Database.Query / transaction query roots reach [ExpressionQueryPlanProvider](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Linq/Planning/Expressions/ExpressionPlanQueryable.cs): parse and capture invocation values, validate the source/backend, then execute. Exact primary-key terminals have a specialized cache path. [SqlQueryPlanBackend](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Linq/Planning/Sql/SqlQueryPlanBackend.cs) routes entity cursors, direct SQL projections, local projections and scalar execution. Creating a lazy cursor is distinct from its first row advancement; that advancement reaches the provider open/execute/read boundaries above.
- **Prepared queries (S1).** [PreparedQuery / PreparedSequenceQuery](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Linq/PreparedQuery.cs) bind fresh argument values during Execute; BindParserOwned captures invocation values and validates the selected source. A sequence remains lazy after this capture. Plans own no live connection. Enumerators own their active reader/command, but borrow the source/transaction lifetime. Current cancellation checks surround synchronous operations; they do not interrupt an in-flight database command.
- **Fluent Select, raw rows, keys and scalar columns (S4).** [Select](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Query/Select.cs) ReadReader is an iterator with command/reader using scopes. ReadRows decodes selected columns; ReadFirstRow eagerly opens/reads/disposes; ReadKeys and ReadPrimaryAndForeignKeys use the same reader pipeline, the latter buffering grouped keys. Scalar terminals execute directly. Early enumerator disposal must release resources. Raw reader rows are cursor views, not independently retained row snapshots.
- **Raw command paths (S4).** ReadOnlyAccess / Transaction.GetFromQuery and DatabaseAccess ExecuteReader/Scalar/NonQuery expose lower-level execution. Raw transaction mutations must preserve their existing cache invalidation policy; SQL text alone does not provide the typed StateChange capture/hydration guarantees. Borrowed IDbCommand handling is distinct from owned string commands.
  [ReadOnlyAccess.GetFromQuery/GetFromCommand](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Mutation/ReadOnlyAccess.cs) lazily constructs RowData from reader fields and calls InstanceFactory.NewImmutableRow with its source. Do not assume this direct raw-materialization path has every cache behavior of a validated expression query or canonical key lookup.

Existing coverage includes QueryExecutionContractTests, QueryPlanSnapshotTests, PreparedQueryTests, EmployeesSqlQueryTests, RawMutationCommandTests, DatabaseAccessReaderLifetimeTests, CommandOwnershipTests and ReaderConnectionOwnershipTests. W1/W2 still need deterministic suspension, combined tokens, cancellation between rows, overlapping operation rejection, early disposal, failed cleanup and source-lifetime tests. W3 must compile/run actual emitted positive and negative consumers; current synchronous tests cannot satisfy that gate.

## Keys, Materialization And Relations

**Owner: W1 capture/publication coordination → W2 row loading → W3 navigation/key surfaces.**

- **Primary/provider/model key lookup (S2 K01–K05).** Generated/InstanceFactory/database/transaction helpers reach [TableCache row loading](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Cache/TableCache.RowLoading.cs). Hits avoid provider execution and record cache metrics. Misses capture a read generation, load canonical rows through [DataSourceAccessSourceRowLoader](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Cache/DataSourceAccessSourceRowLoader.cs), decode provider values and publish only against a valid generation. Singular loads check a second row for cardinality. Legacy batch loading is bounded to 500 keys; preserve requested ordering/deduplication and normalization boundaries.
  [TableCache.RowLookup](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Cache/TableCache.RowLookup.cs) retains null-key handling and the existing null-source fallback to the database's ReadOnlyAccess. Relation index-cache hits can avoid the index query before fetching rows by key. These provider-key contracts differ from Memory.Find's single-column model-valued key contract.
- **Single-reference navigation.** [ImmutableForeignKey](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Instances/ImmutableForeignKey.cs) checks the source-specific holder, then null-key handling, then primary-key lookup or relation-index rows with SingleOrDefault. Loading/model construction occurs outside loadLock. Subscription and publication check both clear/read generations and invalidation. The holder itself can represent null; do not infer the generated required-navigation contract merely from that holder. W3 must verify the accepted required-missing exception in generated sync and async consumers.
- **Collections and implicit lazy loads.** [ImmutableRelation](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Instances/ImmutableRelation.cs) materializes a source-specific snapshot outside its short lock, subscribes, then validates publication. Count, enumeration, values and keys can cause a cold load. Concurrent cold calls can perform redundant loads today; the proposed async shared-load coordinator does not exist yet. Clear invalidates the generation; it must prevent stale publication after a suspended load.
- **Materialization and byte ownership.** Canonical row decoding precedes generated model creation and identity-cache publication. Provider-owned buffers must never escape as mutable shared row state. SQL projection and Memory paths share selected conversion/materialization contracts, not necessarily provider I/O or cache telemetry.

Existing coverage includes RelationSnapshotPublicationTests, RelationCacheInvalidationPrecisionTests, EmployeesPublicCacheInvalidationTests, EmployeesRelationAndThreadingTests, TypedIdRelationKeyNormalizationTests, TypedIdImplicitRelationProjectionTests, ProviderKeyRelationCacheTests and BinaryBufferOwnershipTests. Missing future proof: cancellation per waiter versus shared work, invalidation during actual suspension, private lifetime across awaits, no cache publication after canceled/failed load, and sync/async interleavings.

## Mutations, Transactions And Completion

**Owner: W1 operation/recovery model → W2 provider completion → W3 callbacks and mutation APIs.**

- **Construction and first use.** Database.Transaction / provider.StartTransaction construct a lazy [Transaction](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Mutation/Transaction.cs). The first command triggers [SQLiteDatabaseTransaction](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.SQLite/SQLiteDatabaseTransaction.cs) connection open, committed-visibility PRAGMA and deferred serializable begin, or [SqlDatabaseTransaction](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.MySql/Shared/SqlDatabaseTransaction.cs) pooled open, ReadCommitted begin and optional USE command. Transaction telemetry begins after provider begin. Unused disposal does not open a database connection.
- **Attachment.** AttachTransaction validates a compatible active provider transaction on an open connection. Existing attachment consumes that transaction: completion must occur through the DataLinq wrapper, which may close/dispose the connection. Do not describe this as a new borrowed callback handle. W3's callback borrowing restrictions are a separate accepted API contract.
- **Insert/update/save/delete (S3).** Database/model convenience APIs route through transaction-owned [StateChange](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq/Mutation/StateChange.cs). Capture and preflight precede provider execution; a change becomes single-attempt when execution starts. Auto-increment insert uses ExecuteScalar and decodes the generated key; other writes use ExecuteNonQuery. Transaction-local cache changes, authoritative reload, relation impact keys, mutable lifecycle finalization and successful-change recording follow. Failures poison mutation state and invalidate touched mutables. Mutation activity spans statement/key finalization, while broader transaction orchestration also performs hydration/publication.
- **Commit.** The managed exclusive operation calls provider commit before applying successful changes to shared state, removing transaction cache entries and promoting touched mutables. Provider failure leaves completion uncertain; a post-commit local failure is a different outcome, preserved by TransactionCommitFinalizationException. Neither may become an automatic write retry.
- **Rollback/disposal.** Managed rollback and disposal finalize uncommitted/uncertain state, collect cleanup failures and publish deferred status. Provider Close rolls back an open transaction, then closes the connection; Dispose disposes connection/transaction. Current provider cleanup has sequential synchronous calls, not an async drain/recovery implementation. W2 must prove cleanup after every initialization/commit/rollback failure, including failure before DbTransaction assignment.
- **Commit callbacks.** Current Database/provider Commit(Action/Func) uses a transaction scope, invokes synchronously and commits, with disposal on exit. The accepted async callback ownership, draining unfinished work and bounded automatic rollback are new contracts, not behavior demonstrated by this baseline.

Existing coverage: TransactionMutationGuardTests, TransactionMutationFailureTests, TransactionFaultInjectionCharacterizationTests, EmployeesTransactionLifecycleTests, EmployeesTransactionFailureTests, EmployeesTransactionCommitPublicationTests, EmployeesTransactionCommitOutcomeTests and EmployeesTransactionTrackingTests. The initial W0 quick run also found an intermittent parallel SQLite transaction failure; see the evidence index. Do not convert that failure into async feasibility evidence.

W1 must provide controllable phase/failure tests and immutable captured inputs across suspension. W2 must establish actual cancellation classification, completion certainty, rollback budget behavior and safe cleanup on each provider. W3 owns callback overload binding and borrowed-handle negative consumers.

## Metadata, Probes, Provisioning And Setup

**Owner: W2 native operations → W3 public factory/probe surfaces; W5 runtime validation.**

- **Boolean probes.** Database forwarding reaches provider DatabaseExists/TableExists/FileOrServerExists. [SqlProvider](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.MySql/Shared/SqlProvider.cs) queries information_schema; its reachability probe catches exceptions and returns false. [SQLiteProvider](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.SQLite/SQLiteProvider.cs) uses file existence (or true for named memory), and table probing enumerates sqlite_master. W2/W3 must distinguish cancellation/unsupported capability from absence. File.Exists remains synchronous.
- **Metadata import (S5 A04).** PluginHook selects the registered metadata factory. [MetadataFromMySqlFactory](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.MySql/MySql/MetadataFromMySqlFactory.cs) / [MetadataFromMariaDBFactory](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.MySql/MariaDB/MetadataFromMariaDBFactory.cs) query generated information-schema models, with additional index/column queries and SHOW CREATE VIEW. [MetadataFromSQLiteFactory](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.SQLite/MetadataFromSQLiteFactory.cs) owns a memory keeper lease while enumerating sqlite_master and PRAGMA metadata. Iterated readers are disposed by their enumeration scopes. Server factories construct an information-schema Database without an explicit using/disposal scope in ParseDatabase; W2 must address its owning lifetime when implementing the new path, not assume automatic disposal.
- **Empty/missing/Include baseline (AAPI-108).** Null/empty Include selects all; name matching is case-insensitive. Missing requested tables/views produce InvalidModel. Zero discovered tables/views also produces InvalidModel, rather than an empty successful import. Existing CatchAll/Option behavior is not the proposed live-schema validation result policy. W5 must separate readable-empty, missing expected objects and operational failure without disguising cancellation as absence.
- **Timeout plumbing (AAPI-109).** The baseline has no runtime-validation command-timeout override propagated through these generated information-schema queries and provider command creation. Current driver/connection defaults or caller-supplied command settings apply. W2/W5 must carry the new validation timeout to every metadata command, including additional queries, and retain separate cancellation and rollback-budget semantics.
- **Provisioning (S5 A09–A11).** PluginHook forwards metadata generation into [SqlFromMetadataFactory.CreateDatabase](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.MySql/Shared/SqlFromMetadataFactory.cs) or [SqlFromSQLiteFactory.CreateDatabase](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.SQLite/SqlFromSQLiteFactory.cs). Each directly opens a connection and executes Sql.Text, outside DatabaseAccess command telemetry. Both create a local command without its own using scope. SQLite may synchronously create a file and establish a named-memory keeper. MySQL prepends CREATE DATABASE/USE. Effects are not atomic; failure is not permission to drop, retry or remove files.
- **Preserved constructor/setup I/O.** SQLite provider construction acquires a keeper for named memory and sets WAL synchronously. [SQLiteConnectionStringFactory](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.SQLite/SQLiteConnectionStringFactory.cs) opens keeper connections. [MariaDBProvider](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.MySql/MariaDB/MariaDBProvider.cs) synchronously queries @@version in its constructor, catches failure and conservatively disables UUID support. These are accepted synchronous exceptions, not hidden promises of async construction. Journal-mode command completion does not verify the effective mode.

Existing coverage includes ExistenceQueryTests, ProviderMetadataFailureTests, ProviderMetadataRoundtripTests, MetadataFromServerFactoryTests, MetadataFromSQLiteFactoryTests, SchemaComparerScalarStorageProviderTests and IdentifierEscapingTests. Runtime schema validation and its startup/DI integration do not yet exist: W5 owns live metadata/results and W4 owns hosting integration. W6 adds fixture support against established contracts; it must not invent a separate execution engine.

## Owning Roots, Memory And Extension Boundaries

- **Database/provider disposal (T02).** Database.Dispose delegates to its provider. DatabaseProvider disposes State/cache; SqlProvider disposes its MySqlDataSource in finally; SQLiteProvider disposes state and then its keeper lease. W1/W2 must establish owned-resource cleanup and owned-maintenance shutdown before async disposal, preserving cleanup failures. AAPI-61 requires callers to finish dependent transactions/readers first; it does not authorize root-level cancellation/draining of that application work. The later [W1 owning-root contract](W1%20Owning%20Root%20Disposal.md) provides bounded internal evidence, not native provider adoption. An async extension default cannot pretend that a custom synchronous provider supplies native async.
- **Memory backend.** [MemoryDatabase](https://github.com/bazer/DataLinq/blob/7e36614b5f26f1dd199ff93bc60620f4b0714d5f/src/DataLinq.Memory/MemoryDatabase.cs) owns a read-only seeded store and materialization cache. Query and single-column model-key Find are in-process; seeding snapshots values before publication. Existing query validation rejects unsupported shapes. There is no SQL connection, transaction, mutation, raw reader, database provisioning or SQL metadata factory to wrap. W1/W3 must implement only accepted read capabilities, preserve validation/cancellation timing and avoid Task.Run. Memory integration tests and the nine-row lane do not prove SQL provider behavior.
- **Legacy/custom extensions.** Existing IDatabaseAccess, IDataLinqDataReader, provider factories and external subclasses are the compatibility boundary. The 0.9.2 package/API baseline is distinct from this execution map. W3 must prove additive placement and unsupported defaults with real old/custom consumers. API snapshots alone cannot prove binary consumer execution, generator binding, cancellation or behavior.
- **Local construction and explicit exclusions (S7 X01–X12).** Query/From composition, preparation, Mutate/property assignment, SQL generation, ToDbCommand and unopened GetDbConnection do not perform the execution mapped above. IDataLinqDataWriter.ConvertValue is local encoding. Cache clearing and lifecycle notifications retain synchronous contracts. Obsolete throwing fluent mutation Execute methods remain unsupported. Memory prepared execution, mutation/transactions, SeedAsync and expanded generated navigation/key sources are excluded. Raw native handles are escape hatches: bypassed operations do not acquire managed tracking, retry or cleanup guarantees.
