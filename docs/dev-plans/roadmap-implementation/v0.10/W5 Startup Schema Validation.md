# W5: Startup Schema Validation

**Prepared:** 2026-10-31.

**Audited source:** `967fbc17bf98f05098d5892f3db95c8043293158` on `codex/0.10-w4`, initially clean.

**Status:** Audit and design discussion complete. W5-D01–D06 were accepted on 2026-10-31; W5-D07 was accepted on 2026-11-01. Ready to enter W5.0 contract/base verification and W5.1 metadata implementation. Exact public declarations and all implementation/verification gates remain open. No production code changed for this plan.

W5 lets an application compare its finalized DataLinq model with fresh live database metadata, inspect a complete structured result, and optionally prevent host startup. W4 supplies the registration identity and ownership model. W1/W2 supply substantial async metadata execution; W5 must connect those foundations without confusing import behavior, comparison findings, and operational failure.

The audit is of this checkout, not a new assertion about remote PR acceptance or integration. The [W4 execution record](W4%20DI%20Hosting%20and%20Unit%20of%20Work.md) preserves its own implementation and review evidence. Before implementation, establish the actual W5 base on `v0.10`; do not relabel historical evidence as a run on this checkout.

## 1. Scope and accepted contracts

Authority: [W5 wave](Implementation%20Order%20and%20Integration%20Plan.md#w5-startup-schema-validation), [V10](README.md#v10-startup-schema-validation), [Schema Validation Hooks](../../providers-and-features/Schema%20Validation%20Hooks.md), AAPI-66/67 and AAPI-106–109 in [Async Public API Decisions](Async%20Public%20API%20Decisions.md), and H10-1/H10-4/H10-9/H10-10 in [DI and Hosting Integration](../../architecture/Dependency%20Injection%20and%20Hosting%20Integration.md).

These decisions are already accepted and should not be reopened as ordinary implementation choices:

- Runtime API: `Database<T>.ValidateSchema`, `EnsureSchemaValid`, their async counterparts, and static `DataLinqSchemaValidator.Validate[Async](IDatabaseProvider, ...)`. Synchronous methods must execute synchronously, not block async methods. Async methods must use the supported provider execution path, not `Task.Run` around synchronous import.
- Runtime deployment requires no `datalinq.json`, user companion file, model source files or development checkout. Use finalized compiled model metadata already attached to the registered provider, its effective connection and explicit runtime validation options. Runtime `Include` is an optional model-selection list, not a request to load the tooling configuration's Include setting; null/empty compares all model objects under the normal scope contract. Host configuration sources are application-owned, with no required file format. Verify this boundary with an isolated published consumer.
- Core package placement: validator/options/result in `DataLinq.Validation`, result-based exception in `DataLinq.Exceptions`, hosting integration under an extension namespace. No separate hosting package, Tools dependency, source parsing, or ASP.NET Core dependency in core.
- Options: `FailOnSeverity = Error`, `TreatValidationIssuesAsFailures = true`, nullable `CommandTimeout`, `Include`, and `MetadataReaderLog`. Invoke per-call configuration once synchronously; capture values and copy Include before suspension.
- Results: internally constructed, getter-only identity/counts, read-only difference/issue snapshots and captured-policy flags. Retain every difference, including Info. Copy diagnostic context-message collections. Keep references to finalized metadata without claiming deep cloning. The public validation exception preserves its supplied result.
- `HasDifferences` means any difference. `HasFailures` means a difference meets the threshold or typed issues exist while issue-based failure is enabled. Reject undefined severity values; difference and diagnostic severity enums have different numeric ordering.
- Include scopes both comparison inputs using finalized-model database table/view names. Null/empty means all. Under D06's AAPI-108 amendment, reject invalid names before validation metadata I/O: MySQL/MariaDB use exact compiled-model database spelling and deduplicate identical selections, while SQLite retains its known comparer. Resolve server live-name matching afterward. Do not mutate metadata or forward this list to import readers. Counts describe compared objects. Foreign keys owned by selected tables retain their referenced identities without expanding scope.
- Live reads are fresh, use effective provider identity, own only temporary resources, and do not borrow an application transaction. Readable empty metadata is valid input; missing/unreadable/incomplete metadata is an operational failure. No permanent schema cache or atomic concurrent-DDL snapshot guarantee.
- Command timeout: null preserves the native default; zero means unlimited; positive values round up to seconds; reject negatives and values above 2,147,483 seconds before I/O. This is neither a connection-opening timeout nor an overall deadline. Startup/caller cancellation and recovery rollback budgets are separate.
- Hosting is explicit opt-in, with fail-startup, warning-only, and disabled policies. Targets preserve model/key identity and reuse default aliases. Disabled validation must not activate otherwise-unused registrations. Multiple targets require deterministic order and failure aggregation.
- W5-D01: warning-only permits startup after completed policy-failing comparisons, including typed issues, without changing result flags/severities. Configuration, activation, capability, connection, incomplete-read and timeout failures still block startup. Cancellation propagates after owned work settles. No best-effort mode that continues after operational failure is included in W5.
- W5-D02: attached and central target selection share W4's canonical model/key identity. Apply built-in defaults, host defaults, then target overrides; global Disabled wins. Deduplicate alias/unconfigured selections, allow only one explicit target configuration owner, and reject missing targets or enabled setup with no selected targets. Use W4 instance/factory registrations for supplied databases; defer arbitrary provider-factory validation targets. Retain existing activation semantics and freeze effective validation settings before execution. Exact public signatures remain an implementation review gate.
- W5-D03: one internal `IHostedLifecycleService` adapter validates in `StartingAsync`, before normal hosted-service `StartAsync` methods, including web-server startup, and retains that phase barrier with concurrent service startup enabled. Application-owned migrations must finish before `host.StartAsync` or run at deployment time; custom sequencing uses the direct validator with the automatic hook disabled. Constructors and other lifecycle callbacks can have independent side effects. Forward startup cancellation and settle owned work; arbitrary synchronous activation cannot be forcibly interrupted.
- W5-D04: validate enabled canonical targets sequentially in first-selection order. Collect completed comparisons and independent target operational failures after resource settlement, then apply D01. Reject startup with one public host-specific exception carrying read-only ordered outcomes, including successes; never fabricate a result for an unread target. Configuration, callback/logger and orchestration failures stop scheduling while preserving completed outcomes. Cancellation stays cancellation after settlement. No automatic retries, parallel target execution or persistent report cache.
- W5-D05: log actual errors and useful comparison messages without sanitization, with concise entries and full in-process context. Preserve original exceptions/stacks, failure trees and secondary cleanup evidence; use normal host exception chaining and inspectable outcomes. Reserve the result exception for completed policy failure and preserve cancellation. Application logging controls filtering and framework verbosity. Do not append connection configuration dumps or add a MariaDB message-sanitization change. Exact public members and key-display details remain API review.
- W5-D06: read `@@lower_case_table_names` once per server validation read on the same owned session; use identifier-specific rules consistently and reject ambiguous names without silently retaining the first. Unreadable/uninterpretable settings fail validation. Exact MySQL/MariaDB Include spelling is validated against compiled provider metadata before validation metadata I/O; no `datalinq.json` or new public casing option is required. Preserve SQLite and existing CLI/import behavior; carry an immutable runtime comparison context through sync/async paths.
- W5-D07: emit structured issues for the accepted catalogue of detected representation limits, independently of logging, with internal typed ownership/object/aspect identity. Include SQLite generated/hidden-column detection. Scope issues to relevant objects while retaining global/unknown scope, and withhold only claims invalidated by known omissions. Preserve every provable difference, original messages and operational failure. Issues fail policy by default independently of difference severity; disabling issue-based failure retains them. Do not broaden general SQL feature support or alter CLI/import behavior.
- No creation, migrations, repair, interactive startup secret prompts, generator database access, or MSBuild integration. W6B testing fakes and W8/W9 performance/release acceptance retain their existing boundaries.

Some older specification paragraphs describe plumbing that has since landed. The source inventory below determines what W5 must implement; the older sketches are not evidence that it is all missing or that their exact hosting overloads are final.

## 3. Accepted design decisions

W5-D01–D07 are **accepted**, with dates and scope recorded below. These settle behavior, not implementation completion or exact public declarations. The bounded choices and consumer/API verification in sections 4–6 remain part of implementation work.

### W5-D01: What warning-only permits

**Accepted by the user:** 2026-10-31. Resolves the operational-failure boundary for the three host policies. Runtime validation already requires operational failures to remain failures; this decision also fixes their effect on startup.

**Decision:** warning-only softens completed comparisons, including policy-failing typed issues. Missing secrets, activation errors, unsupported runtime validation, failed/incomplete reads and command timeouts still prevent startup. Startup cancellation always stops further validation and propagates after owned work settles; it is never logged-and-continued as drift. A healthy comparison with warnings below threshold already passes in fail-startup mode.

| Outcome | Fail-startup | Warning-only | Disabled |
| --- | --- | --- | --- |
| Completed result, `HasFailures == false` | Report; continue | Report; continue | Do not run |
| Completed result, `HasFailures == true` | Report; reject startup | Report unchanged result; continue | Do not run |
| Target configuration/activation/capability failure | Reject startup | Reject startup | Do not activate target |
| Connection/metadata/timeout failure | Reject startup | Reject startup | Do not run |
| Startup cancellation | Stop scheduling, settle owned work, propagate | Same | No target work; host owns its cancellation |

Failure thresholds and issue policy determine a completed result's `HasFailures`; host mode determines whether that result prevents startup. Warning-only never rewrites `HasFailures`, difference severities, or retained issues to imply success. Disabled mode skips validation and does not activate otherwise-unused targets.

**Alternative not selected:** best-effort startup continuation after operational validation failures. W5 has no such fourth policy. D02 separately settles target selection/configuration; D04 settles sequential collection and public aggregate outcomes without relaxing this startup policy. Callback exception projection, exact public mode spelling and issue production retain their separate D05/API-review/D07 gates.

**Verification required:** the full table above, unchanged structured results across fail-startup/warning-only, original cancellation propagation with resource settlement, and no activation/database access from disabled validation.

### W5-D02: Target API, settings precedence and duplicates

**Accepted by the user:** 2026-10-31. Accepts both selection styles, canonical model/key targeting, ordered defaults/overrides, alias deduplication, one explicit target configuration owner, W4 ownership reuse and the existing provider-activation boundary. This accepts the behavior and API direction, not uncompiled exact declarations or the D03 startup phase.

**Decision:** support registration-attached `ValidateSchemaOnStartup(...)` on both W4 builder forms, plus a central `AddDataLinqSchemaValidation(...).ValidateDatabase<TDatabase>(...)` family selecting an unnamed/default or explicit keyed registration. Names/overloads are illustrative; compile representative calls before freezing them. Use an explicit host mode (`FailStartup`, `WarningOnly`, `Disabled`) rather than overloading a severity threshold to mean disabled.

- Resolve central selections to canonical W4 registration descriptors at startup preflight, after service registration has finished. This allows validation to be declared before a provider registration and allows either `.AsDefault()` fluent order.
- Keep one hosted adapter. Maintain target descriptors in first-selection order and canonicalize aliases before any provider activation. Keys use the registration's equality semantics, never stringification or sorting.
- Apply built-in defaults, then host-wide validation defaults, then target-specific overrides. Copy all options into immutable per-run snapshots before the first database activation. A global Disabled mode overrides targets; a target may also be disabled. Reject invalid modes/thresholds/timeouts and malformed Include entries without constructing providers. Checking Include against finalized provider metadata may require activation, but must precede validation metadata I/O.
- Repeated unconfigured selections of the same canonical registration are idempotent, including an unconfigured central selection of an attached target. Allow only one explicit per-target configuration owner; reject a second explicit configuration even if its values happen to match. Do not compare callback behavior or choose an order-dependent winner. Host-wide defaults are not a competing per-target owner. Two different canonical registrations sharing an externally supplied provider remain two explicit targets; only actual aliases are deduplicated. Never deduplicate by connection string or physical database.
- An unkeyed request resolves the unnamed registration or explicit default. Never select an arbitrary key or enumerate every registration of a model.
- Diagnose missing/ambiguous requested registrations without I/O. An enabled registration with no targets should fail configuration rather than appear to have validated anything; a globally disabled adapter need not resolve targets or connection settings.
- Use W4 `UseInstance`/`UseFactory` for externally supplied databases. Defer arbitrary `ValidateProvider(Func<IServiceProvider, IDatabaseProvider>)` targets: they have no canonical registration identity or reliable alias deduplication and introduce another ownership contract. The direct provider-level runtime API remains available. This supersedes the older raw provider-factory hosting sketch; it does not remove direct provider validation.

The API review must settle callback timing, duplicate configuration diagnostics and the exact options/builder signatures. Avoid ambiguous `object? key` versus configure-delegate overloads. No live options reload or hidden `BuildServiceProvider()` is needed.

Retain W4's normal activation semantics: enabling startup validation can construct the selected provider and trigger existing setup I/O. The no-creation/no-journal-change guarantee applies to the observational reader; it does not retroactively make SQLite construction observational. Disabled validation performs no such activation. W5-D02 does not add a provider-construction redesign or promise that the entire enabled startup path is observational.

**Verification required:** compile attached/common/provider-typed and central forms; prove key/default identity and first-selection order without early activation; test declarations before provider registration and both default-selection orders; verify defaults/overrides, global/target disablement, immutable snapshots, duplicate-selection idempotence and duplicate-configuration rejection even for equal values. Cover missing/default/empty selections, equal keys, distinct registrations sharing an instance, separate containers, missing secrets under global disablement and W4 borrowed/transferred ownership. D03 separately settles when the adapter executes; D04 settles execution/aggregation of multiple targets.

### W5-D03: Startup phase and external migrations

**Accepted by the user:** 2026-10-31. Settles the lifecycle phase, internal adapter, application-owned migration ordering, constructor-side-effect boundary and cooperative startup cancellation. D04 separately settles target aggregation and public outcomes; D05 settles operational exception projection and actionable diagnostics without sanitization.

**Decision:** use `IHostedLifecycleService.StartingAsync` for the validation barrier, with no validation in `BackgroundService.ExecuteAsync` or an `ApplicationStarted` callback. Keep the adapter internal; applications use the D02 registration helpers or the direct runtime validator. Its constructor receives descriptors/services, not resolved databases. Normal hosted workers and the web server must not enter `StartAsync` until validation completes and D01 permits startup, including when `ServicesStartConcurrently` is enabled.

The pinned Hosting 10.0.11 [Host implementation](https://github.com/dotnet/runtime/blob/v10.0.11/src/libraries/Microsoft.Extensions.Hosting/src/Internal/Host.cs) completes the StartingAsync phase before invoking hosted StartAsync methods and logs exceptions escaping startup. This supports a pre-listener barrier even when service starts are concurrent. Hosted service construction happens earlier; other components' constructor side effects are outside this guarantee. This records the accepted design, not completed implementation evidence.

For applications running migrations, complete application-owned orchestration before `host.StartAsync`, or run deployment-time migrations followed by startup validation. A migration implemented in another hosted service's `StartAsync` is too late for this gate. Other `StartingAsync` callbacks are not a supported migration-ordering mechanism, particularly with concurrent service startup. If the application needs a custom sequence, it can call the runtime validator explicitly and disable the automatic hook. W5 does not discover migration tools, reorder hosted services or add a general startup-dependency scheduler.

Forward the host startup cancellation token through the validation runner and its owned reads. Cancellation stops further target scheduling and propagates after owned work settles; do not abandon active database work to manufacture a hard deadline. It cannot interrupt an arbitrary synchronous registration factory or the existing MariaDB constructor probe. The host deadline therefore remains cooperative; the per-command timeout remains separate and does not bound activation.

**Verification required:** actual Generic Host and HTTP fixtures must prove that pending validation blocks normal worker/listener startup, required failure prevents startup, and warning-only permits startup after a completed comparison. Exercise concurrent startup and both registration orders, cancellation with owned-resource settlement, and an explicit pre-host migration sequence. Document constructor and independent lifecycle-callback side effects without claiming the gate prevents them.

### W5-D04: Multi-target execution and the host failure contract

**Accepted by the user:** 2026-10-31. Settles sequential collection, the public structured startup exception/outcomes and the stopping rules below. Exact public names/members remain an API-review gate; D05 separately settles failure projection and diagnostic rendering.

**Decision:** validate enabled targets sequentially in canonical first-selection order. Continue to other independent targets after a completed comparison failure or ordinary target operational failure; abort the run on cancellation and on orchestration/configuration/callback failures that make further execution unreliable. This means fail-startup prevents serving, rather than necessarily abandoning the first failing target.

Retain an ordered per-target outcome containing either the planned runtime `DataLinqSchemaValidationResult` or an operational failure, with canonical target identity. Include successful comparisons as well as failures; there must be no synthetic comparison result for an unvalidated target. After temporary resources settle, apply D01 across the outcomes and, if startup must be rejected, throw one host-specific startup exception with read-only ordered outcomes. The exception/outcome surface is public so applications can inspect multiple failures; it is supporting host evidence, not another schema-difference model or a public arbitrary runtime-result builder.

**Continuation rules:** detect descriptor/selection/settings errors during preflight wherever possible and reject the run before target I/O. A later configuration failure still aborts the run. An isolated connection/read/command-timeout failure is recorded against that target; continue to independent targets only after its owned work settles. Do not treat every caught exception as an ordinary target failure: a broken orchestration invariant, or a configuration/metadata callback or logger throwing, stops further scheduling and fails startup. Preserve any completed outcomes and attach the run-level failure without inventing a comparison result. Exact failure classification and exception projection must be reconciled with D05.

Sequential collection can delay failure reporting when later targets are slow, but gives one diagnostic pass over independent databases without concurrent activation, interleaved callbacks or additional connection bursts. For example, if A has policy-failing drift, B cannot connect and C matches, attempt C before rejecting startup. Warning-only would soften A but still reject B under D01. This continuation never permits the application to serve after an operational failure.

Freeze public type/member names during API review without reopening the accepted behavior/public inspectability. Preserve completed results when later targets fail. Cancellation stops further scheduling, settles owned work, then propagates as cancellation, with earlier results available through already-emitted diagnostics; a persistent host report cache is not required. Do not add retries, parallel target execution, a global database lock or abandoned timeout tasks.

**Verification required:** stable order; all-success and mixed outcomes; per-target modes; no later target before prior settlement; preflight rejection; callback/logger aborts; public inspection of successful, failed and preserved earlier outcomes; no fabricated comparisons; and cancellation with no later activation. Fail-startup must not be mistaken for stop-on-first-target-failure in tests or documentation.

### W5-D05: Operational exceptions and actionable diagnostics

**Accepted by the user:** 2026-10-31. Accepts the revised exception and diagnostic contract below: actual errors and useful metadata differences without sanitization, concise logs, complete in-process context, normal exception chaining and preserved cancellation. The earlier redaction, generic-message, restricted diagnostic-accessor and MariaDB sanitization proposals are rejected. Exact public names/members and detailed log/key formatting remain API-review choices.

The async reader returns failures as `IDLOptionFailure` except for cancellation. The public validator returns a result, so it needs an explicit exception mapping. Failure objects may contain original exceptions, aggregates, local metadata failures or callback failures. [DLOptionFailureException](../../../../src/DataLinq.SharedCore/Exceptions/DLOptionFailureException.cs) already exposes its failure and renders failure text. [SchemaDifference](../../../../src/DataLinq.SharedCore/Validation/SchemaDifference.cs) retains the kind, severity, path and original comparison message. Reuse that diagnostic content instead of replacing it with generic codes.

**Decision — runtime failures:** direct runtime calls preserve original provider/callback exception objects, stack information and execution context where available. Rethrow a single underlying exception only when doing so loses no additional failure-tree evidence; use a dedicated operational wrapper for exception-free or composite failures, retaining the original failure tree and ordered secondary evidence. A read failure followed by cleanup failure must retain both, with the original primary/secondary relationship. Reserve `DataLinqSchemaValidationException` exclusively for completed comparisons that fail policy. Ordinary invalid-argument/unsupported-capability exceptions remain ordinary errors, and cancellation remains cancellation. Exact names/members remain API review; do not discard evidence or change established execution precedence.

**Decision — host exception:** D04's public startup exception exposes its ordered outcomes and original operational failures through ordinary inspectable properties. Preserve normal exception chaining: a single causal exception can be the original `InnerException`; multiple operational failures can be represented by an aggregate while retaining target associations in the outcomes and preserving existing nested failure trees. The summary identifies failed targets and causes. Comparison-only rejection keeps the full comparison results without inventing a provider exception. There is no prohibition on raw inner exceptions or requirement for a special diagnostic accessor. The pinned [Generic Host implementation](https://github.com/dotnet/runtime/blob/v10.0.11/src/libraries/Microsoft.Extensions.Hosting/src/Internal/Host.cs) logs startup exceptions before rethrowing them, so a full framework exception log remains possible even when DataLinq's own entries are concise. Do not suppress or rewrite exception details to force the framework to emit a short message; the application owns logging configuration.

**Decision — log presentation:** emit one concise target summary and actionable per-finding/per-failure entries. Include target/model/provider identity, failure stage where known, exception type and actual message, available provider error code, and difference kind/path/severity/message. Retain expected/actual defaults, comments and other metadata when they explain the mismatch. Concision comes from avoiding repeated object dumps and stack traces in every DataLinq entry, not from scrubbing words, redacting values, replacing errors with generic descriptions or silently truncating the cause. More verbose context can use normal logging levels while full structured results, original exceptions, stack information and secondary failures remain inspectable in process. Do not independently append a full connection configuration dump; received error messages remain unchanged even if they contain connection details. Any application-required filtering belongs in its logging pipeline. This W5 direction does not change the existing, separately configured SQL parameter-value logging policy.

Diagnostic target formatting must not alter canonical key equality/order or make validation depend on arbitrary key formatting code. Ordinary string/enum/numeric keys can be shown unchanged; complex keys can use their type and stable target ordinal. That fallback is about dependable identification, not content sanitization. Finalize exact key display rules with the host API review.

Classify failures using the operation boundary and retained execution evidence, not message parsing or exception type alone. A callback throwing a provider exception still follows D04's callback-abort rule. If the logger itself throws, stop scheduling after owned work settles and preserve its original error; do not repeatedly invoke the same failed logger to report it. Propagate cancellation with the relevant token and existing failure/cleanup evidence; do not add a cancellation wrapper solely to control log output or convert cancellation into D04's aggregate startup failure. The Generic Host may still wrap exceptions itself.

**Verification required:** capture DataLinq and framework logging, including structured state, and prove that actual error and comparison messages remain available without sanitization. Test representative defaults/comments and provider messages containing connection-like text. Verify useful target/stage/error-code context, concise entries without repeated full graph dumps, public exception identity/stack/context and secondary-failure access, mixed outcomes, cancellation, callback-origin classification independently of exception type, and no recursive invocation of a failed logger. These replace the proposed secret-absence tests.

The [MariaDB constructor](../../../../src/DataLinq.MySql/MariaDB/MariaDBProvider.cs) already includes `ex.Message` when version detection fails. The proposal to replace it with a generic fallback message is withdrawn; no sanitization correction is required for W5. Preserve version-detection behavior and its unsupported-feature fallback. Routing console output through normal logging could be considered separately, while retaining the actual cause, but is not added as a W5 prerequisite.

### W5-D06: Server name comparison and before-I/O Include validation

**Accepted by the user:** 2026-10-31. Settles live server identifier matching, exact compiled-model Include selection before validation metadata I/O, ambiguity/failure handling and the explicit AAPI-108 amendment. Includes the runtime deployment clarification below. Implementation and native-provider evidence remain required.

**Runtime-source clarification:** "model names" means `Table.DbName` in the compiled model metadata already available through `provider.Metadata`. D06 does not read `datalinq.json` or import/generation settings. Runtime `Include` comes from explicit validation options (or defaults to all); `@@lower_case_table_names` comes from a SQL query on the existing provider's database connection. No part of the startup design requires the development configuration file. The CLI retains its separate configured source-file workflow.

The audit found that current server comparison requires configuration but behaves ordinally; it does not read `lower_case_table_names`. The [MySQL identifier rules](https://dev.mysql.com/doc/refman/8.4/en/identifier-case-sensitivity.html) and [MariaDB identifier rules](https://mariadb.com/docs/server/reference/sql-structure/sql-language-structure/identifier-case-sensitivity) make table/database matching depend on that setting: `0` is case-sensitive; `1` and `2` compare without case sensitivity, with different storage behavior. Columns and index names have their own case-insensitive rules. Reusing the current comparer unchanged can report a missing/extra pair for table names the server considers equal. The client operating system and ordinary data collation do not substitute for the live server setting.

**Decision:** read `@@lower_case_table_names` once per validation read on the same owned server metadata session, within the existing command-timeout/cancellation/resource boundary, and pass an immutable runtime comparison context to the existing comparer. Sync and async paths must agree. Do not infer the setting from the application's OS, require a duplicated user setting or cache it globally. Failure to read or interpret a supported setting means this target cannot complete validation; surface an operational failure under D01/D04 rather than silently using ordinal matching. Keep SQLite's established comparison rules without an additional server-setting query.

Apply name rules by identifier kind: table references embedded in foreign keys must follow table-name matching, while column references in keys/indexes follow column-name matching. Preserve identifier spelling in results and diagnostics. Do not lowercase whole foreign-key/index signatures, SQL expressions, defaults or comments; that would change unrelated semantics. Validate metadata selection/grouping as well as final comparison so the reader does not merge distinct case-sensitive objects before comparison. Verify non-ASCII cases with provider evidence; do not assume a culture-dependent .NET comparison reproduces server rules.

Reject ambiguous model/live names under the effective rules where they affect scope resolution or compared objects; never silently retain the first collision as `BuildTableLookup` currently can. For a full comparison, a model declaring both `Orders` and `orders` is valid as two distinct table identities only on a case-sensitive server. On a case-insensitive server, report the conflicting identities and fail validation rather than choose one or report a completed comparison. Model ambiguity is configuration failure; inconsistent live metadata is an operational failure. Distinct names on a case-sensitive server remain distinct.

**Accepted amendment to [AAPI-108](Async%20Public%20API%20Decisions.md#aapi-108-validation-include-is-comparison-scope-and-empty-schemas-are-valid-input):** require exact canonical model database spelling for MySQL/MariaDB Include names before validation metadata I/O, then resolve live comparison rules and detect effective-name collisions after reading server configuration. For a model mapped to `Orders`, `Include = ["Orders"]` selects it; `Include = ["orders"]` is invalid unless that exact model table/view also exists. Repeated identical selections deduplicate; null/empty still selects all. After selection, the live server may legitimately match selected `Orders` to live `orders`. SQLite retains its known comparer. Existing D02 provider-construction effects remain outside the before-metadata-I/O guarantee. This supersedes the original requirement to use the live server-aware name comparer for pre-I/O Include selection/deduplication.

The accepted split keeps model selection deterministic before metadata I/O while live identity matching follows the server. The cost is that Include is deliberately stricter about spelling than SQL on a case-insensitive server; provide an error that identifies the canonical model spelling when unambiguous. It adds no new public case-sensitivity option. The alternatives of duplicating server comparison settings in application configuration or retaining an ordinal fallback are not selected.

**Verification required:** real case-sensitive and insensitive MySQL/MariaDB fixtures; supported mode-2 evidence where available with platform limitations stated; same results in sync/async; query timeout/cancellation/cleanup and invalid-setting failures; exact Include spelling and deduplication before validation metadata I/O; correct live scope/counts; preserved case-sensitive distinct tables; clear ambiguity failures; identifier matching inside foreign keys/indexes; unchanged case-sensitive literal/default/comment content; and native non-ASCII name cases. Controlled tests cover otherwise unreachable configurations without being presented as native provider proof. Avoid changing the existing import/CLI comparator's default contract incidentally when adding runtime-specific context. No database or model renaming is part of W5.

### W5-D07: Typed issues from successful but limited metadata reads

**Accepted by the user:** 2026-11-01. Settles structured limitation reporting, the initial catalogue and SQLite detection, typed ownership/aspect scoping, narrowly withheld comparison claims, and the existing independent issue-failure policy. Logging-independent production, unchanged useful messages, operational-failure separation and CLI/import compatibility are required. Exact internal categories and transport implementation remain review details.

The accepted result supports typed issues, but successful readers currently supply only metadata. Skipped generated columns, unsupported indexes/defaults and unresolved referenced objects often produce only human log messages. Concrete branches exist in the [server parser](../../../../src/DataLinq.MySql/Shared/MetadataFromSqlFactory.cs), [native server reader](../../../../src/DataLinq.MySql/Shared/MetadataFromSqlFactory.Async.cs), [SQLite catalog parser](../../../../src/DataLinq.SQLite/MetadataFromSQLiteFactory.Catalog.cs) and [SQLite default parser](../../../../src/DataLinq.SQLite/MetadataFromSQLiteFactory.cs). AAPI-107 permits an empty issue list when the reader supplies no typed issues, but implementing W5 that way would leave known limitations out of the result and can cause false differences.

**Decision:** emit structured issues for known detected representation limits during a successful runtime read. Add a private typed collector/read result alongside the metadata path, publishing public `DataLinqDiagnosticIssue` snapshots through the accepted `Issues` property. Retain typed ownership, object identity and affected comparison aspect internally so scope and comparison never depend on parsing display messages or formatted paths. Emit at the branch that detects the limitation. Issue production must work with logging disabled; configured callbacks and existing import warning text/behavior remain intact. Preserve original useful messages under D05 without sanitization. Avoid introducing a new public metadata extension protocol or arbitrary result builder.

**Accepted initial catalogue:**

| Detected limitation | Initial coverage | Required distinction |
| --- | --- | --- |
| Unsupported generated column | Existing MySQL/MariaDB parser branch; SQLite runtime detection described below | A column exists but its generated semantics were not represented; do not assert that it is absent. |
| Unsupported index form | SQLite partial/expression/descending indexes; server expression/prefix-length/descending/invisible-or-ignored forms where detected | Retain owner/index identity and reason; do not call the observed index missing merely because it was omitted. |
| Omitted default | SQLite unsupported/blob defaults; existing server zero-date-default omission | Only default comparison lacks evidence; retain independent type/nullability/key comparisons. |
| Omitted index/relationship because required objects were not represented | Existing missing imported column/referenced-object branches | Track the owning table and affected object; malformed catalog rows and failed reads remain operational failures. |

These known support-limit issues normally retain Warning severity, with useful failure category/path/message/context. Exact internal reason categories and deterministic deduplication/order are implementation-review details; an empty Issues list does not certify all conceivable SQL features or invisible objects. Preserve existing failed-Option behavior for unsupported cases currently classified as failure unless separately agreed; this decision is not a blanket downgrade of unsupported exceptions.

**Additional detection required:** the current SQLite runtime reader uses `pragma_table_info`, which does not report generated or hidden columns; [SQLite documents](https://www.sqlite.org/pragma.html#pragma_table_xinfo) `table_xinfo` as the fuller source. For runtime validation, use that information to detect omitted generated/hidden columns and retain their identities as limitations, without pretending to support their generation expressions or changing CLI/import model-generation behavior. Keep normal-column interpretation and every new/readjusted query inside the same timeout/token/cleanup path in both sync and async execution. Failed detection is an operational failure, not an issue-only success. This bounded detection addition prevents silent omissions that a log-only collector could not see.

**Comparison interaction:** retain all provable differences, and suppress only the specific comparison claim invalidated by a known omission. For example, if `ix_active_orders` was observed but omitted because it is partial, report that limitation instead of `MissingIndex` for that same object. If a column's default was omitted, withhold only a default mismatch that cannot be established; still compare the column's supported properties. Use D06's identifier rules and typed aspect identities, never a blanket table-wide suppression or message matching. Unknown identity provides no license to hide unrelated differences. A genuinely absent object in successfully acquired metadata remains a normal missing-object difference.

**Include:** retain database-wide issues and issues owned by compared objects. Omit an out-of-scope issue from the scoped result only when typed ownership proves it unrelated; unknown scope stays visible. A relationship owned by a selected table still matters when its referenced table is outside Include. This is comparison scoping, not presentation filtering: retain every issue inside the resulting scope regardless of log level or failure-policy setting. Operational read failure anywhere still fails execution under the existing contract; Include does not promise reduced I/O or error suppression.

**Policy:** retain AAPI-107's default `TreatValidationIssuesAsFailures = true`. With only a known limitation and no differences, the result can have `HasDifferences == false`, nonempty `Issues` and `HasFailures == true`. Fail-startup rejects it; warning-only reports the same result and permits startup under D01. Setting `TreatValidationIssuesAsFailures = false` keeps every scoped issue and removes only its contribution to `HasFailures`; real differences still follow `FailOnSeverity`. A Warning issue can therefore block fail-startup even with `FailOnSeverity = Error`, because the issue switch is independent of the difference threshold. A timeout, failed query, malformed required metadata or callback failure still throws and blocks startup in both enabled modes. Do not convert incomplete acquisition into a completed limited result.

**Alternative not selected:** leave Issues empty and retain log-only omissions. That would lose programmatic coverage information and leave preventable false differences. Implement the accepted catalogue and narrow omission-aware comparison in W5 without expanding general SQL feature support. A genuinely issue-free successful read still returns an empty Issues collection.

**Verification required:** each catalogue family; default-aspect versus whole-object identity; SQLite generated/hidden detection; sync/async parity; identical issues with logging enabled/disabled; defensive snapshots; retained original messages; deterministic order/deduplication; exact suppression versus genuine missing objects; D06 casing; selected/out-of-scope/global/unknown issue ownership; issue/threshold/host-mode truth table; unchanged operational and callback failure propagation; and CLI/import regression fixtures. Any newly discovered successful-read omission must receive an explicit disposition during the implementation audit, not be silently promoted to full support.

## 4. Bounded implementation choices

These require code/API review, but not another broad architecture discussion:

- Initial live validation capability: built-in SQLite, MySQL and MariaDB paths. Memory has no independent live SQL schema and must fail explicit validation as unsupported, not compare its model to itself. Legacy/custom readers without the required capability fail explicitly before I/O; do not dispatch solely from `DatabaseType` or add a general public metadata extension protocol. Verify inherited built-in providers without claiming all derived overrides are supported.
- Use a private synchronous companion to the existing provider metadata contracts. Share catalog SQL and local parsing where practical, but retain actual sync connection/command/reader/disposal operations and async counterparts. Do not change an import factory's public virtual behavior to implement runtime validation.
- Add an internal comparer entry point over selected existing `TableModel` references plus comparison context. Keep finalized parent/relation graphs intact. Avoid building a reduced metadata graph that loses foreign-key targets. Exclude stubs and non-table/view objects consistently from name validation, scope and counts.
- Use the provider's effective reported `DatabaseName` for the runtime result; carry model/key target identity separately in hosting. Confirm alignment with live metadata and normalized names, especially SQLite named-memory databases. Do not derive a new connection/path identity or add connection details to the result.
- Freeze hosted options once per run and keep the service single-run per normal host lifetime; repeated-start behavior must be explicit and tested, without caching direct runtime validation results.
- Compare after successful metadata acquisition and cleanup. Check cancellation before comparison/publication; document cooperative cancellation during bounded synchronous comparison, or add internal checkpoints if needed. Do not publish an async result after observing cancellation.
- Add `Microsoft.Extensions.Hosting.Abstractions` in core at the repository's reviewed Microsoft.Extensions version. Full host implementations remain test/consumer dependencies. Check platform and transitive package effects, particularly Memory-only consumers and generator isolation.
